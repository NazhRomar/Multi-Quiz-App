# Part 3: PM Fundamentals, Stakeholders, and RTM

## Key Definitions
- **Project:** a *temporary* endeavor with a unique goal and usually a budget.
- **Project Management:** applying processes, methods, skills, knowledge, and experience to hit objectives within scope, time, cost, and quality, while meeting stakeholder expectations.

## Why PM Matters
1. **Improved efficiency:** better resource allocation, productivity, and cost savings
2. **Stakeholder satisfaction:** clear communication builds trust
3. **Organization & structure:** turns chaos into efficient processes
4. **Risk management:** identify, assess, and mitigate risks early
5. **Strategic goals:** projects drive organizational change

## What a PM Does
Planning (scope, schedule, resources, budget), Execution (leading the team), Communication (updating stakeholders), Risk Management, and Problem-Solving (handling conflicts and challenges).

## The 8 Project Performance Domains
Interrelated areas that work together: **Stakeholders, Team, Development Approach & Life Cycle, Planning, Project Work, Delivery, Measurement, Uncertainty.**

## Stakeholder Performance Domain

**Desired outcomes:**
- Productive working relationships with stakeholders throughout
- Stakeholder agreement with project objectives
- Beneficiaries are supportive; opponents don't negatively impact outcomes

**Definitions:**
- **Stakeholder:** anyone (person, group, organization) who may affect, be affected by, or *perceive* they're affected by the project.
- **Stakeholder Analysis:** systematically gathering info to decide whose interests to consider.
- **Stakeholder Management:** identify stakeholders, analyze expectations and impact, and plan how to involve them.

**Who they are (inner to outer circle):**
- Inner: Project Manager, PM Team, Project Team
- Middle: Governing Bodies, PMOs, Steering Committees
- Outer: Suppliers, Customers, End Users, Regulatory Bodies
- Also: top management, your manager, peers, resource managers, internal/external customers, government, contractors/subcontractors, and others (public, landowners, interest groups, competitors)

**Stakeholder Management Tools:**

| Tool | Purpose |
|---|---|
| Power-Interest Matrix | Efficiency and better relationships |
| Cooperation-Threat Matrix | Better engagement strategies |
| Stakeholder Register | List of stakeholders and groups |
| Stakeholder Analysis Template | Better relationships, higher success odds |
| Communication Plan | Keeps everyone informed and engaged |

**Stakeholder Register:** a living table used throughout the project. It tracks interests, involvement, interdependencies, influence, all interactions (planned or not), and who on the team is responsible. Closely tied to the communication plan.

**Power/Interest Grid:**

| | Low Interest | High Interest |
|---|---|---|
| **High Power** | Keep Satisfied | Manage Closely |
| **Low Power** | Monitor | Keep Informed |

Questions to ask: Who are they? What are their interests? Will interest change over time? Can coalitions be built?

**Cooperation-Threat Matrix:**

| | Low Threat | High Threat |
|---|---|---|
| **Low Cooperation** | Marginal → Monitor | Non-Supportive → Defend |
| **High Cooperation** | Supportive → Involve | Mixed Blessing → Collaborate |

**Project Sponsor:** responsible for enabling success, usually outside the project, **signs off on completion** (the one the PM must satisfy), escalates issues beyond the PM's control, and helps create the charter and plan.

**Politics & relationships:** Supportive stakeholders are essential. Consider the environment, each group's goals (stated and hidden agendas), and power. Build respect by being honest, taking ownership, being reliable, standing by decisions, and owning mistakes. Cultural differences affect communication, negotiation, and decision-making.

## Requirements Traceability Matrix (RTM)
A document that tracks every requirement through design, development, and testing.

**Purpose:** track requirements, ensure full coverage, support change management.

**Typical columns:** Requirement ID, Description, Source, Related Test Cases, Design/Implementation Details, Verification Status, Priority.

**Types:**
- **Forward:** requirement → design → code → tests
- **Backward:** every product element traces back to a requirement
- **Bi-directional:** both, so changes ripple correctly either way

**Benefits:** requirement compliance, defect prevention, project visibility, easier audits.

**When to use:** requirement analysis, design, testing/validation, maintenance/upgrades.

**Tools:** Excel; JIRA, HP ALM, IBM DOORS; Trello, Confluence with add-ons.

**Challenges:** complexity at scale, frequent updates, manual errors.
**Best practices:** start early, review with stakeholders, automate where possible.

### RTM Exercise (Online Learning Platform)
**Scenario:** a university platform for course materials, quizzes, grades, instructor communication, progress tracking, and data privacy compliance.

**Steps:**
1. **Identify requirements** and split into functional and non-functional (e.g., User Login, Course Material Access, Quiz Functionality, Data Privacy Compliance)
2. **Create the template** with columns: Requirement ID, Description, Type (F/NF), Design Spec Reference, Development Reference, Testing Procedure, Status (Pending / In Progress / Completed)
3. **Populate** each row (e.g., RQ-01 Secure login, F, Login Module p.4, Module 1A, TC-01, In Progress)
4. **Develop test cases** (TC-01 valid/invalid login, TC-02 materials load, TC-03 quiz grading correct, TC-04 security review and penetration test)
5. **Track status** as work progresses (coded but untested = In Progress)
6. **Analyze gaps** for missing design, dev, or test steps, and adjust for new or changed requirements

**Deliverables:** (1) completed RTM spreadsheet, (2) testing procedure document, (3) 1 to 2 paragraph reflection on how RTMs protect quality and prevent missed requirements or tests.

# Part 4: Project Selection & Chartering (Weeks 4 to 5)

## Core Idea
- **Project Selection ("speed dating for ideas"):** IT has limited budget, time, and developers but many ideas. Leadership picks the one with the most business value.
- **Project Charter ("birth certificate & contract"):** officially creates the project, states why it exists, and **authorizes the PM** to assign resources and spend funds.

## Initiating Workflow
**Business Need** (problem or opportunity) → **Selection Criteria** (financial and non-financial filters) → **Business Case** (cost vs. benefit proposal) → **Project Charter** (authorization and PM assignment)

## Financial Selection Criteria
- **Payback Period** = Initial Investment ÷ Annual Net Cash Inflow
- **ROI** = (Net Profit ÷ Total Cost) × 100
- **NPV:** total expected gain with future cash flows discounted to present value

## Non-Financial Drivers (can override ROI)
- **Regulatory compliance** (e.g., Central Bank AML laws, Data Privacy)
- **System reliability** (avoiding catastrophic downtime)
- **Competitive necessity** (matching industry baselines)
- **Social responsibility** (SDG goals like decent work and economic growth)

## Case: EduTech Solutions

| Factor | A: Cloud Migration | B: Mobile QR Feature |
|---|---|---|
| Initial Cost | $150,000 | $50,000 |
| Payback | 2.5 years | 1.0 year |
| ROI | 15% | 35% |
| Strategic Goal | Stability & SLA compliance | Market differentiation & growth |
| Main Risk | Migration downtime | Low faculty adoption |

**Outcome:** B has the better ROI, but **A was chosen** because stability during exam weeks is non-negotiable.

## 6 Key Elements of a Charter
1. **Project Purpose:** the business problem or opportunity
2. **SMART Objectives:** specific, measurable, achievable, relevant, time-bound
3. **Scope Boundaries:** high-level deliverables **and explicit exclusions**
4. **Key Constraints:** deadlines, tech limits, funding caps
5. **Summary Milestones:** high-level timeline of check-ins and phases
6. **PM Authority:** decision-making and financial thresholds

## Case: Zenith Bank Digital KYC
- **Problem:** 40% customer drop-off from a 3-day manual account process
- **Project:** a "10-Minute Digital KYC Onboarding Module" using OCR and facial recognition
- **Constraints:** AML laws, third-party biometric API dependency, legacy overnight batch processing

**Sample charter:**
- **Purpose:** cut drop-off from 40% to under 10%
- **Success criteria:** account creation under 10 minutes; handles 5,000 concurrent verifications
- **Constraints:** budget capped at $200,000; non-negotiable 6-month go-live before Q4
- **PM authority:** can reallocate up to 10% of contingency funds and approve schedule changes under 5 days without board review

## Charter Pitfalls
- ❌ **Too high-level:** a "blank check" that invites scope creep
- ❌ **Too detailed:** putting a WBS in the charter forces constant rework
- ✅ **Balanced:** high-level goals, clear constraints, defined PM thresholds

> **Key line:** The Charter authorizes **WHAT** and **WHY**. The RTM and WBS define **HOW**.

**Discussion prompt:** A sponsor says to skip listing exclusions. What risks does that create, and how would you explain that out-of-scope items protect the budget?

## Charter Assignment Checklist
- **Key Personnel:** project title, executive sponsor, designated PM
- **Strategic Value:** business purpose linked to organizational strategy
- **Targets:** SMART objectives, quantifiable success criteria
- **Boundaries:** high-level scope, deliverables, constraints, risks
- **Empowerment:** PM authority level signed off by the sponsor

# Part 5: Module 4B: WBS & WBS Dictionary

**Why it matters:** Week 8 scope management topic, tested in **Long Test 2**, and required for the final **Project Management Plan**.

## Learning Objectives
- Understand how the WBS sets the baseline for scope control
- Apply the **100% Rule** (no gaps, no overlaps)
- Build a WBS Dictionary with acceptance criteria and owners
- Tell apart deliverable-based WBS items from task-based activity lists

## What a WBS Is
Without one, engineers work in silos (e.g., login screens built without API specs, separate payment databases, cloud set up with unverified tools), which leads to chaos, duplicated effort, missed requirements, and schedule slips.

A **WBS** breaks the project into small, **deliverable-oriented** pieces called **Work Packages**, so everyone knows exactly what's in scope.

## Scope Baseline = 3 Parts
1. **Approved Scope Statement:** scope, major deliverables, assumptions, constraints
2. **WBS:** hierarchical breakdown of all work
3. **WBS Dictionary:** descriptions, acceptance criteria, cost, and owners per package

> **100% Rule (Golden Rule):** The WBS covers 100% of the scope, including internal, external, and PM work. No more, no less.

## Example WBS: Cloud Banking Application Migration
```
1.0 Cloud Banking Application Migration
├── 1.1 Project Management & Governance
│   ├── 1.1.1 Project Charter & Planning Documents
│   └── 1.1.2 Stakeholder Communication Reports
├── 1.2 User Authentication Module
│   ├── 1.2.1 Multi-Factor Authentication (MFA) Engine
│   └── 1.2.2 OAuth2 Single Sign-On Integration
├── 1.3 Core Financial Services
│   ├── 1.3.1 Account Balance API
│   └── 1.3.2 Real-time Fund Transfer Engine  [Work Package]
└── 1.4 Cloud Infrastructure & Security
    ├── 1.4.1 AWS Production Environment Provisioning
    └── 1.4.2 Database Encryption & PCI-DSS Compliance
```

## Example Dictionary Entry (1.3.2)

| Field | Detail |
|---|---|
| Code & Name | 1.3.2 Real-time Fund Transfer Engine |
| Parent | 1.3 Core Financial Services |
| Description | Design, build, and integrate RESTful microservices for interbank transfers using ISO 20022 message formats |
| Owner | Lead Backend Engineer (Fintech Core Team) |
| Acceptance Criteria | (1) Latency under 1.5 s per transaction at peak load; (2) 100% ISO 20022 audit logging compliance; (3) zero critical vulnerabilities in static and dynamic scans |
| Effort / Cost | 60 hours / $9,000 USD |

## Anti-Patterns to Avoid

**1. The Task-List Trap (verbs instead of nouns)**
- ❌ 1.1 Write Python Code, 1.2 Test Code, 1.3 Fix Bugs (ongoing actions, can't confirm completion)
- ✅ 1.1 Auth Microservice, 1.2 Test Execution Report, 1.3 Staging Deployment (clear, acceptable outputs)

**2. Wrong sizing**
- **Over-decomposed (under 8 hours):** admin overhead and micromanagement
- **Under-decomposed (over 80 hours):** hidden cost overruns and delays
- Sweet spot: **8 to 80 hours** per work package

## Waterfall vs. Agile Scope

| Factor | Waterfall (WBS) | Agile (Backlog) |
|---|---|---|
| Hierarchy | WBS → Control Account → Work Package | Epic → Feature → User Story |
| Timing | All upfront before execution | Iterative (backlog refinement) |
| Scope Control | Formal Change Request via Change Control Board | Backlog re-prioritized each sprint |
| Best For | Fixed scope, regulated, infrastructure | Evolving products, mobile apps, SaaS |

## Case: QuickMart Scope Creep
- **Context:** grocery app, 4-month hard deadline, $120,000 budget
- **Problem:** Week 3, Marketing informally asks for an AI recommendation engine, and the lead dev starts building it
- **PM response:** (1) check the WBS: it's not there; (2) flag it as scope creep; (3) freeze the work and file a formal Change Request showing the impact (+$18k, +3 weeks) before approval

## Student Challenge (flawed WBS)
```
1.0 Campus Event Management System
├── 1.1 Talk to Student Council Representatives
├── 1.2 Design Database Schema & ERD
├── 1.3 Write Backend Code in Node.js
└── 1.4 Perform Integration Testing
```
Problem: every item uses an action verb (Talk, Design, Write, Perform). Tasks: identify at least two errors, rewrite Level 2 as nouns, and write one testable acceptance criterion for a new deliverable.

## Takeaways
- Scope Baseline = Scope Statement + WBS + WBS Dictionary
- Structure around **outputs (nouns)**, not actions (verbs)
- **If it's not in the WBS, it's out of scope**

2. **Work Description:** technical scope and work required
3. **Deliverable Output:** the tangible artifact (e.g., .sql migration scripts, ERD document)

5. **Assigned Role / Owner** (e.g., Lead Database Engineer)
6. **Assumptions & Constraints:** dependencies, boundaries, platform limits

## Rubric

| Criteria (Weight) | Excellent (5) | Good/Fair (3) | Unsatisfactory (1) |
|---|---|---|---|
| **Structure & Decomposition (30%)** | Levels 1 to 4, deliverable-oriented, grouped by phase/module | 2 to 3 levels, mostly task lists | Flat, disorganized task list |
